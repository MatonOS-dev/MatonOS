### Steam install loop: root cause
- **Android package visibility.** Stubs and the subsystem only query the package `org.matonos.linux` plus an intent action. No generated package answered that action, so:
  - the subsystem saw only the app stubs, and never one runtime;
  - the Steam stub's lookup of the installed 26.08 Platform runtime got NameNotFound.
- So the stub called `repairDependency` → `LinuxAppStoreService.repair(appRef)`. That reinstalls the **whole graph, including the Steam stub**, which kills the stub; it restarts and repairs again.
- I tried an `openPackage` AIDL call (the subsystem looks the package up for the stub). It didn't help, because the subsystem can't see runtimes either. The user chose to revert it, and it is reverted.

### Current change set
- `StubGenerator`:
  - every generated package (apps and runtimes) gets an inert exported `org.matonos.linux.stub.PackageService` that answers action **`flatpak.PACKAGE`**, guarded by `BIND_JOB_SERVICE` so only the system can bind;
  - the queries in generated stubs use `flatpak.PACKAGE` (`PACKAGE_ACTION`);
  - `STUB_VERSION_CODE` 23 → 24.
- New class `stub/PackageService.java`: an empty Service, `onBind` returns null.
- App and bootstrap `AndroidManifest.xml`: the query is now `flatpak.PACKAGE`.
- **The `x<hash>` suffix is dropped** from `DeployManifest.packageFor` (user decision). Package names change, e.g. `flatpak.runtime.org_freedesktop_Platform.x86_64.v26_08`.
  - No migration code ([[no-migrations]]). Reinstall all Flatpak packages on the VM.
  - `linux/stubgen/tests/ForegroundManifestTest.java:60` still uses a hashed name literal. That's harmless (it's a fixture), but update it if a test compares generated names.
