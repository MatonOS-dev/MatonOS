# Installer v1 app-owned A/B profile and operation API

This is the v1 policy profile generated by `rn-apps/installer`, not a layout
policy enforced by the service. The app owns the 16 GiB minimum, GPT sizes,
10.5 GiB super, 5 GiB slot group capacities, member sizes, source mapping and
operation order. A future app version may choose another valid layout or
sequence without changing the generic executor API. The service still
independently rejects unsafe devices, invalid bounds, malformed operations
and non-live requests.

## V1 GPT profile

All sizes use binary MiB/GiB. App aligns starts to 1 MiB, reserves GPT backup
space at the disk end, and assigns all remaining space to userdata.

| # | Name | GPT type | Size | Purpose |
|---:|---|---|---:|---|
| 1 | `esp` | EFI System `c12a7328-f81f-11d2-ba4b-00a0c93ec93b` | 512 MiB | FAT32; fallback `\\EFI\\BOOT\\BOOTX64.EFI`, systemd-boot and loader config. PARTUUID passed as `androidboot.boot_part_uuid`. |
| 2 | `boot` | XBOOTLDR `bc13c2ff-59e6-4262-a352-b275fd6f7172` | 1 GiB | FAT32 shared boot filesystem; slot-specific files and entries. |
| 3 | `misc` | Linux filesystem `0fc63daf-8483-4772-8e79-3d69d8477de4` | 4 MiB | Cleared boot-control compatibility state; no filesystem required. |
| 4 | `metadata` | Linux filesystem | 64 MiB | Android metadata. |
| 5 | `super` | Linux filesystem | 10.5 GiB | Two LP groups, LP metadata and headroom. |
| 6 | `addons_a` | Linux filesystem | 512 MiB | Writable ext4 partition for signed add-on ZIPs and per-add-on folders matching slot A's kernel. |
| 7 | `addons_b` | Linux filesystem | 512 MiB | Writable ext4 partition for signed add-on ZIPs and per-add-on folders matching slot B's kernel. |
| 8 | `userdata` | Linux filesystem | Remainder | ext4, formatted for Android userdata initialization; starts empty. |

V1 app minimum is **16 GiB**. Nominal fixed allocation is about 13.2 GiB
including the 1.5 GiB ESP/boot, 10.5 GiB super, both 512 MiB add-on slots,
misc/metadata and alignment; about 2.9 GiB remains for userdata on a 16 GiB
disk after GPT tail reserve. Exact userdata bytes are computed from the
freshly enumerated disk capacity by the app and shown before confirmation.
The executor does not enforce 16 GiB or any of these partition sizes; it
checks that the submitted table is aligned, nonoverlapping, unique, and within
the exact selected disk.

## Dynamic partition profile

LP metadata size: 64 KiB; metadata slots: 3. The app defines two groups, each
with 5 GiB maximum capacity:

| Group | Members (logical image capacity per slot) | Total |
|---|---|---:|
| `pc_dynamic_partitions_a` | `system_a` 2048 MiB; `system_ext_a` 512 MiB; `product_a` 1536 MiB; `vendor_a` 960 MiB; `odm_a` 64 MiB | 5120 MiB |
| `pc_dynamic_partitions_b` | `system_b` 2048 MiB; `system_ext_b` 512 MiB; `product_b` 1536 MiB; `vendor_b` 960 MiB; `odm_b` 64 MiB | 5120 MiB |

Both slots therefore provide 10 GiB aggregate read-only system capacity.
Current EROFS images are substantially smaller than these logical capacities.
V1 copies live `_a` images into A and then clones A to B. The first OTA writes
the inactive group. The profile may be revised by the app if image growth
requires it; the service only verifies declared group/member sums fit inside
the selected `super` extent and refuses overflow. Each writable `addons_<slot>`
partition is managed by the add-on service: it accepts one signed ZIP per
add-on, verifies its manifest/signature, then extracts to one folder per
add-on. An update stages new-kernel modules into the inactive slot's partition
before switching OS slots.

## Boot files and systemd-boot counting

The installed disk uses one ESP and one XBOOTLDR. Signed UKIs and boot entries
live on the ESP; the formatted XBOOTLDR remains available for later boot
assets. The live image carries signed live, debug-live, installed-A and
installed-B UKIs. Installed UKIs embed the correct fstab suffix, slot suffix,
and live=0 property. The live UKIs use the live fstab suffix, slot A, and
live=1.

The installed ESP contains EFI/BOOT/BOOTX64.EFI, shim's `grubx64.efi`
second stage, systemd-boot, the two slot UKIs, loader.conf, and loader entries
A+3-0.conf / B+3-0.conf. Each entry passes the target ESP PARTUUID as
`androidboot.boot_part_uuid`; first-stage init uses it to identify the boot
disk and create installed GPT `/dev/block/by-name` links. The app also derives
`androidboot.boot_devices` from the selected disk's sysfs ancestry as a
compatibility hint. Each entry sets `androidboot.hardware`, the
installed `androidboot.fstab_suffix`, and its own `androidboot.slot_suffix`;
the UKI embeds matching values. systemd-boot counts attempts by renaming the
entry. The boot-control HAL stores slot state
in misc, changes loader.conf when selecting a slot, renames a successful entry
to A.conf or B.conf, and marks an unbootable entry with a non-conf extension.
Firmware boots the fallback EFI path; no EFI NVRAM writes are used.

The live image stays bootable with its live-specific fstab selection. Its
compact super contains only *_a logical images; installation copies A and
clones A to B. The installed GPT includes addons_a and addons_b, each 512 MiB.

## Generic operation API v1

The bridge's existing `install` channel authorizes the privileged installer
package using its pinned signing certificate and normal bridge permission.
It transports one operation per request; the app retains the ordered plan and
decides whether to submit the next request. Progress and cancel are scoped to
the current primitive. Representative JSON (camelCase names are the wire
contract; enums are shown as strings):

```json
{
  "apiVersion": 1,
  "targetDiskId": "259:0",
  "targetDiskIdentity": "sys=/sys/devices/...;seq=42;wwid=...;serial=...",
  "operation": {
    "kind": "write_gpt",
    "declaredDiskBytes": 34359738368,
    "diskGuid": "<app-generated-guid>",
    "partitions": [{
      "name": "esp", "typeGuid": "<efi-system-type-guid>",
      "partGuid": "<app-generated-guid>", "startBytes": 1048576,
      "sizeBytes": 536870912
    }]
  }
}
```

`operation.kind` is one of:

| Primitive | App-supplied description |
|---|---|
| `listDrives` | Read-only drive and partition snapshot method (not a destructive operation). |
| `write_gpt` | Exact disk byte count, disk GUID and all partition names/type GUIDs/PARTUUIDs/start/size extents. |
| `create_lp_metadata` | super PARTUUID, metadata size/slot count, group capacities and logical member names/sizes. |
| `format` | Partition reference, `vfat`, `ext4` or `f2fs`, label. |
| `copy_partition` | Source is a named read-only live image member or an identified target partition; destination is an identified target partition/logical member. |
| `clone_partition` | Identified target source and destination; destination must contain source extent. |
| `write_files` | Target ESP/XBOOTLDR, safe relative directory, files with safe relative names and a service-approved live payload ID or inline bytes plus hash. No caller path is accepted. |

`targetDiskId` is only the current major:minor locator. Every primitive also
requires `targetDiskIdentity`, copied from the selected drive snapshot. The
service builds it from the canonical sysfs path and kernel disk sequence,
with normalized WWID/serial values when available. Missing or ambiguous
identity fails closed. Before destructive execution, the service checks
`BLKGETDISKSEQ` on the opened target descriptor; helper tools receive that
held descriptor so a reused device number cannot redirect their writes.

Every destructive request names the selected disk by the current enumeration
ID and uses PARTUUID/logical names rather than `/dev` paths. GPT starts/sizes
must be aligned, unique and nonoverlapping, and fit the enumerated disk with
backup-GPT space. LP metadata and all group/member extents must fit the
declared `super`. Paths must be relative, traversal-free, and payload IDs
must come from the service's fixed live-image source catalog. The daemon
re-enumerates immediately before every write, resolves each reference again,
and fails closed on stale IDs, mount/use state uncertainty or a changed live
source. Service implementation must extend enumeration with liblp logical
partition metadata before logical-partition operations are enabled.

The live-only gate, mounted/in-use and read-only checks, live medium exclusion,
caller certificate authorization, fresh checks, path/extent checks and
progress/cancellation are service safety responsibilities. Layout choices,
minimum drive size, slot scheme, order and
future features are app policy. API changes require a version increment only
when existing operation semantics or wire shapes change; additional
composable operations can be introduced additively while preserving v1.

## User data and live-only installer

User files are intentionally skipped. The installed system starts with an empty
`/data`; no importer, FUSE copy path, staging partition, or first-boot migration
service is included. Android initializes fresh userdata and FBE state on first
boot.

Installed UKIs set ro.boot.matonos.live=0. The init service starts only when
that property is 1, and the Settings Install activity alias is enabled only in
a live session. No marker operation is needed.
