# Desktop title bars: design investigation

## Car SystemUI is the useful pattern

Car SystemUI is an app replacement that statically links stock `SystemUI-core` and the stock `SystemUI-application` startup code, then supplies its own Dagger components. In [`packages/apps/Car/SystemUI/Android.bp`](/mnt/data/aosp/packages/apps/Car/SystemUI/Android.bp#L107) (AOSP source), `CarSystemUI-core-defaults` links both stock libraries (lines 120–126); `CarSystemUI-core` packages Car's application/component sources (lines 171–197); the `CarSystemUI` app links that core and declares `overrides: ["SystemUI"]`, `platform_apis`, `system_ext_specific`, platform signing, and privileged install (lines 218–247). The package is still `com.android.systemui`; its manifest installs `CarSystemUIAppComponentFactory` at lines 75–79 of `packages/apps/Car/SystemUI/AndroidManifest.xml`.

Car replaces both Dagger seams, not just a SystemUI service class. `CarGlobalRootComponent` returns `CarWMComponent.Builder` and `CarSysUIComponent.Builder` ([`CarGlobalRootComponent.java:30-48`](/mnt/data/aosp/packages/apps/Car/SystemUI/src/com/android/systemui/CarGlobalRootComponent.java#L30)); `CarSystemUIInitializer` builds those components ([`CarSystemUIInitializer.java:35-58`](/mnt/data/aosp/packages/apps/Car/SystemUI/src/com/android/systemui/CarSystemUIInitializer.java#L35)). Its `CarWMComponent` substitutes `CarWMShellModule` for the stock WM module ([`CarWMComponent.java:42-52`](/mnt/data/aosp/packages/apps/Car/SystemUI/src/com/android/systemui/wmshell/CarWMComponent.java#L42)); that module provides a `WindowDecorViewModel` ([`CarWMShellModule.java:96-99,164-195`](/mnt/data/aosp/packages/apps/Car/SystemUI/src/com/android/systemui/wmshell/CarWMShellModule.java#L96)). The stock `WMComponent` includes `WMShellModule` ([`WMComponent.java:47-57`](/mnt/data/aosp/frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/dagger/WMComponent.java#L47)); Car instead composes `WMShellBaseModule` and its own form-factor modules. This is the model for a Maton component graph: no copied framework/Shell source, but an app-owned root/WM subcomponent and provider.

Product selection should add `MatonSystemUI` to `PRODUCT_PACKAGES`; its Soong app declares `overrides: ["SystemUI"]`, as Car does. Keep the package and `SystemUIService` component stable, so the default `config_systemUIServiceComponent` remains valid ([`frameworks/base/core/res/res/values/config.xml:3963-3965`](/mnt/data/aosp/frameworks/base/core/res/res/values/config.xml#L3963)). An overlay is only needed if the service component changes. This checkout has no Car product makefile selecting `CarSystemUI`; its module override and component wiring are the concrete source examples.

## WM Shell decoration seam and reuse boundary

Stock `WMShellModule.provideWindowDecorViewModel()` returns the optional `DesktopModeWindowDecorViewModel` when desktop mode is available, otherwise `CaptionWindowDecorViewModel` ([`WMShellModule.java:285-327`](/mnt/data/aosp/frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/dagger/WMShellModule.java#L285)). The desktop model itself is constructed by `provideDesktopModeWindowDecorViewModel()` ([same file:1325-1404](/mnt/data/aosp/frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/dagger/WMShellModule.java#L1325)). The narrow override is the `WindowDecorViewModel` binding in our own WM Dagger component, installed by our own initializer/root component in the same way as Car. Shell consumers depend on the `WindowDecorViewModel` interface ([`WindowDecorViewModel.java:25-110`](/mnt/data/aosp/frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/windowdecor/WindowDecorViewModel.java#L25)).

Reuse the stock Shell task organizer, transitions, transaction queue, display services, task info, and public interfaces. Do not plan on subclassing the stock desktop view model as the customization hook: its public constructor takes a large fixed dependency set and internally creates its decoration wrapper and default header factories ([`DesktopModeWindowDecorViewModel.java:184-187,290-343,1833-1855`](/mnt/data/aosp/frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/windowdecor/DesktopModeWindowDecorViewModel.java#L184)); its decoration lifecycle and factory state are private. Composition around it cannot replace its header layout/actions cleanly. A first custom model will own the `WindowDecorViewModel` lifecycle and decoration UI/actions, reusing Shell primitives where their public constructors/APIs permit. This means reimplementing task decoration creation/disposal, caption interaction, and close/maximize/minimize actions; it does not mean copying stock source.

The stock desktop header layout puts app/menu content at the left and minimize, maximize, close at the right; there is no centered title ([`desktop_mode_app_header.xml:20-24,92-130`](/mnt/data/aosp/frameworks/base/libs/WindowManager/Shell/res/layout/desktop_mode_app_header.xml#L20)). The close/maximize/minimize handlers and task actions live in Shell view-holder/model code. The requested left-side close/maximize/minimize order and centered title therefore need a Maton-owned header/view-holder and model/action wiring. Do not assume an RRO can replace the private Shell layout; first verify overlayability and whether its existing view holder tolerates a reordered layout.

SystemUI can compile against hidden platform APIs in this shape: Car is `platform_apis: true`, platform-signed, privileged, and installed in `system_ext` ([`Android.bp:240-247`](/mnt/data/aosp/packages/apps/Car/SystemUI/Android.bp#L240)). MatonSystemUI needs equivalent build/install properties. This is an in-tree platform build boundary, not an app-facing API promise; avoid depending on private implementation details that churn every AOSP release.

## Client-decorated Linux windows

There is no supported app window flag that removes WM Shell's desktop caption. `WindowInsets.Type.captionBar()` and `WindowInsetsController.hide()` can express an app request, but Shell deliberately force-consumes caption insets for app headers (including when apps request hiding) in [`DefaultWindowDecoration.kt:512-548`](/mnt/data/aosp/frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/windowdecor/DefaultWindowDecoration.kt#L512). `APPEARANCE_TRANSPARENT_CAPTION_BAR_BACKGROUND` only makes the caption background transparent; Shell still draws its controls ([`WindowInsetsController.java:85-97`](/mnt/data/aosp/frameworks/base/core/java/android/view/WindowInsetsController.java#L85)). `FLAG_NO_TITLE` applies to an app's own action bar/title, not the task caption.

The practical zero-framework-patch path is a Maton WM Shell policy keyed by verified task package/UID (or a narrowly scoped System Bridge capability): for Linux client-decorated tasks, create no Android caption and keep the app content's top edge usable. The repository has a prior System Bridge request design for caption suppression and task-bound identity checks, but its caption hook was only proposed as a framework patch and does not implement this no-patch behavior ([`NOTES.md:684-696`](../NOTES.md#L684)). Reuse the bridge authorization concept, then add the actual suppression in our own WM Shell model; do not trust an app's package string alone.

Dragging from the client's own title bar also has no public `View` task-move call: `View.startMovingTask()` exists but is explicitly `@hide` ([`View.java:30099-30117`](/mnt/data/aosp/frameworks/base/core/java/android/view/View.java#L30099)). Linux stub code must not call it directly. Route drag begin/update/end through the System Bridge's existing task-identity check and task-bounds operation (the bridge can use hidden platform APIs); or let the custom Shell model own the pointer stream and move its task. The bridge route fits the current Linux host/client architecture and keeps hidden calls inside the bridge. An ordinary insets appearance request is insufficient for hiding the caption and grants no task movement.

## Independently testable implementation steps

1. **Replacement skeleton:** add a `MatonSystemUI` app and `MatonSystemUI-core` Dagger/application library, linked to stock `SystemUI-core` and `SystemUI-application`; use an app-owned root/WM component and a provider that preserves stock desktop/caption model selection and construction. Select it via `PRODUCT_PACKAGES` and `overrides: ["SystemUI"]`. Build and boot-check SystemUI startup before changing decoration behavior.
2. **Provider seam:** install a Maton `WindowDecorViewModel` provider and verify ordinary desktop/freeform task open/change/close paths, transitions, multi-display handling, and no-decoration fallback. Keep task lifecycle behavior stock-compatible.
3. **Header/actions:** implement the centered title and left close/maximize/minimize controls; verify accessibility, focus, resize, maximize/restore, minimize, and close while other windows keep stock behavior.
4. **Client-decorated opt-in:** add a bridge capability and Shell policy for caption suppression, then bridge-routed drag begin/update/end for the Linux task. Test denial for untrusted callers, opt-in Linux tasks, and normal Android apps retaining captions.

## Risks

- SystemUI's Dagger graph and Shell module set move frequently. A custom root/WM component can fail code generation from duplicate or missing bindings even when source compiles; keep the replacement app minimal and validate each step before adding UI.
- `DesktopModeWindowDecorViewModel` is tightly coupled to private factories and evolving Shell internals. Reusing its implementation without copying source is limited; the custom model will own meaningful lifecycle and interaction code.
- Shell caption policy and the bridge's task capability are hidden/platform-facing seams. Re-check package/UID/task validation, lifecycle races, and module signatures at each AOSP rebase.
- The reference header resources are private to Shell and their overlayability was not established in this source-only investigation. Prefer Maton-owned views until an overlay route is proven.

**First implementation step scope:** create only the replacement app/core module and its Dagger root/WM component skeleton, link the stock SystemUI libraries, rebind the stock desktop/caption view-model selection unchanged, select it as the `SystemUI` override, and prove startup with unchanged decoration behavior. Do not add custom buttons, caption suppression, or drag behavior in that step.
